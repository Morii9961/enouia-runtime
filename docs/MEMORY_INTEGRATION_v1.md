# Memory integration v1

Enouia Runtime is the Windows client for Enouia Memory's local part ([ADR-025](adr/025-enouia-memory-integration.md), companion shell [ADR-026](adr/026-companion-shell.md)). It embeds Memory's workspace Core at a pinned Git revision behind a Runtime-owned adapter. The Memory, Context and Sessions surfaces are Memory's local frontend. The Memory repository owns the domain, the contracts and every cloud stage. Its [integration handoff](https://github.com/Morii9961/enouia-memory/blob/main/docs/integration/RUNTIME.md) lists host duties, known Core behavior and the compatibility log that routes each Memory-side change here.

## Pinned revision

| Field | Value |
|---|---|
| Repository | `https://github.com/Morii9961/enouia-memory.git` (public) |
| Revision | recorded in [docs/integration/memory-pin.json](integration/memory-pin.json), in `apps/desktop/src-tauri/Cargo.toml` and in its `Cargo.lock` |
| Consumed crates | `enouia-memory-workspace`, `enouia-memory-contract` for its command catalog (long-running and write commands), and `enouia-memory-provider` for native text Provider setup (Memory ADR-MEM-48) |
| Contract | workspace IPC v1 (`schemaVersion: 1`, 47 commands) |
| Memory surface digest | the aggregate from Memory's `docs/integration/runtime-surface.json` at that revision |

`node scripts/check-memory-integration.mjs` checks that the pin record, the manifest and the lockfile agree. It also checks that the revision is a full SHA and that no path, branch or `[patch]` source is committed. Given `--memory-checkout <dir>`, it compares the recorded surface digest with that checkout's manifest.

## Adapter (`apps/desktop/src-tauri`)

- **State.** One `Workspace::new(Config::default())` per process, held by `MemoryHost` in `src/memory.rs`.
- **`memory_call(request)`** forwards one workspace IPC v1 envelope. Core errors come back inside the envelope (`kind: "memory_error"`, `{code, retryable, rules}`). Host failures are plain strings: `permission_denied`, `worker_failed`, `runtime_closing`, `runtime_busy`, `root_in_use`, `root_admission_failed`, `root_token_unavailable`.
- **`memory_pick(kind)`** opens a native dialog for `import_file`, `vault_root`, `backup_destination` or `export_folder` and registers the choice with the Core. It returns `{token, displayName, bytes}`, `{cancelled: true}` or `{error}`. The page never receives a path.
- **Scope.** Native `main` maps to `HostSurface::Workspace`, and `overlay` to `HostSurface::QuickSearch` (only `memory_search`). Every other label is refused. Request fields cannot widen the scope. The picker remains main-only.
- **Threading and lifecycle.**
  - Every call runs on `spawn_blocking`.
  - `vault_open`, `vault_create`, `vault_lock` and `vault_unlock` take a gate exclusively. Commits and commands that start operations (import, index rebuild, verify, backup) take it shared, so no work can start on a Vault handle that is closing.
  - Plain reads are not gated. While a lock waits for verify or backup, which cannot be cancelled, status and progress still answer.
  - Vault lifecycle admission hides and clears the overlay before its worker starts. A counted guard refuses search and overlay reopening through all queued lifecycle transitions; status and progress remain available.
  - Closing hides the window to the installed tray and retains the same Core. Tray or Settings Exit starts one asynchronous shutdown: new work is refused, status/progress remain available, external model calls stop locally, import and index work are cancelled, verify/backup are joined, and the Vault and index are released before exit. A local stop does not establish remote cancellation; read saved session outcomes after reopening. A failed shutdown worker restores a recoverable window.
- **Data root.** No root is remembered or opened by default. The owner opens or creates one through the native dialog; creating one needs the typed phrase `create new vault`. The owner can also name a root with `--memory-vault <dir>`. The root must not sit under a Git working tree, a sync folder, Program Files or Windows, and the Core refuses such roots.
- **Runtime root admission.** `src/root_lease.rs` reserves the native directory's Windows volume/file identity before opening or creating a Vault. Cooperating Runtime processes contend on the same kernel presence object even when paths differ. The directory and presence handles remain held while locked, and are released after Core shutdown, a successful switch, or a failed switch that actually closed the old Core. Process termination releases the handles too. A failed occupied-root switch preserves the current Vault. This writes no Vault file and does not change Memory's lock. Other clients do not share this Runtime guard; the pinned Core separately owns its cross-client Vault lock. An adapter test checks refusal and release in both directions between a Runtime host and a bare pinned Workspace on a synthetic root. That is an embedded-Core test, not a real third-party-client acceptance run.
- **Native choices.** The host keeps at most 64 Vault picker-token/path bindings in memory for admission. The page still receives only opaque tokens. Memory remains authoritative for token expiry, consumption and creation confirmation; an evicted token asks the owner to choose again. A startup admission failure leaves canonical status at no Vault, while `shell_status.vaultAdmissionError` supplies a separate host explanation on Home, Memory and Settings.
- **Permissions.** `build.rs` declares the two Memory commands and host window commands. `main-window` grants Memory/picker, window controls, `shell_status`, `shell_show`, `shell_search`, `shell_exit`, `activity_call` and `activity_setup`. The Activity commands reach only the separately installed runner (ADR-028), never the Memory adapter. `quick-search` grants only scoped `memory_call`, `shell_show` (existing main), `shell_hide` (itself) and event listen/unlisten for clearing. Native identities are checked again in Rust. There is no filesystem, process execution, HTTP, dialog, opener, provider or Activity plugin permission. The CSP is `default-src 'self'` with `connect-src ipc: http://ipc.localhost`, `form-action 'none'`, `base-uri 'none'` and `freezePrototype`. WebView2 general autofill is off on both windows, and Memory inputs set `autocomplete="off"`, so the WebView profile keeps no copy of typed memory text.
- **Companion (ADR-026).** Tray (Show, Lock Memory Vault, Exit; left click shows). Global hotkey Ctrl+Alt+M, or another letter with `--hotkey-key`, opens quick search; a conflict is reported in Settings. Opt-in login startup writes only `HKCU\…\Run\EnouiaRuntime` = `"<exe>" --autostart`, which starts in the tray with no Vault.
- **Compatibility and OS exit.** The main window also grants `show_main`, `hide_window`, `exit_app`, `startup_status` and `startup_set`. The active `quick-search` capability grants only `show_main` and `hide_window` compatibility commands, never startup or exit. Both command families use the same tray, hotkey and shutdown implementation. Core companion status preserves `exiting` during shutdown. Windows session end and Restart Manager reach Core shutdown through `RunEvent::Exit` (ADR-027). The tray's Lock runs on a worker thread. `--autostart` starts hidden and ignores even a supplied `--memory-vault` argument.
- **No copies.** The adapter writes no logs and persists nothing. Memory text exists only in the Vault and in the page's memory while a surface shows it.

## Frontend (`apps/desktop/src`)

- **Mode.** Inside the native shell (`isTauri()`), Memory, Context and Sessions use the pinned Core. A browser preview keeps the explicitly labelled fictional demo, unchanged. The header badge states which mode is active ("Memory · Vault open · Inspector demo"). Activity reads the installed producer ([ADR-028](adr/028-activity-surface.md)). The Runtime Inspector stays fictional, and in the native shell its subtitle says so.
- **Client.** `src/memory/client.ts` mirrors Memory's reference client:
  - Request envelope `{schemaVersion: 1, requestId: "req_<uuid>", command, idempotencyKey, arguments}`.
  - One `ui-<uuid>` key per user submission. A retry resends the same payload with the same key.
  - `WRITES` must equal the pinned contract's write commands. A desktop Rust test enforces this.
- **Hooks.** `src/memory/hooks.ts` ports `useAction` and `useLatestRead`. Only the latest read publishes its result, error or busy state. A retry is offered only for `retryable` errors.
  Shared status reads keep Runtime's `shell_status.vaultChanging` separate from Core's canonical Vault slot. A pending lock can have a detached `locked` Core slot while Runtime is still joining workers; the UI keeps waiting/progress feedback and withholds Unlock until Runtime releases admission. See [real long-work lifecycle evidence](validation/Long-operation-lifecycle-v1.md).
- **Surfaces** (`src/memory/*.tsx`), drawn in the Quiet Runtime language:
  - **Memory Vault.** Candidate inbox with accept, edit-and-accept or reject through the review plan and its confirmation code; remember-a-statement; the canonical explorer with literal search, history and paging; detail with evidence and source excerpts; correction proposals; delete-impact preview; forget and purge plans; Import; Vault and recovery: open/create/unlock/lock, verify, index rebuild, backup to an empty folder, restore preview.
  - **Sessions.** Branch list, transcript, unfinished turns, provisional checkpoints, asking the local Mock, and a link to the capsule behind an answer.
  - **Context.** Compile preview, the inclusion and exclusion decisions, and dispatches with the verified actual request.
  - **Home and Settings** show the Vault state and Memory's component states from `workspace_status`. Memory's fixed `activity` row is not shown; Activity keeps its own surface. Settings also shows the quick-search hotkey state, the login-startup switch and Exit. The Runtime Inspector's component descriptions stay documentation references.
  - **Quick search** (`src/shell/QuickSearch.tsx`, the `?view=overlay` page): scoped literal search over approved memories, with a link that opens the main window. Search/Retry completion restores typing focus only when it has not moved elsewhere; query edits and window clearing invalidate that handoff. See [synthetic focus and observation evidence](validation/Quick-search-focus-v1.md).
- **Error text.** `workspace.vault_in_use` and the `root.*` reasons (Memory ADR-MEM-46) read as owner text; `vault_in_use` offers no Retry.
- **Rendering.** Memory and source text render as plain text nodes only. There is no Markdown or HTML rendering and no link navigation. Source excerpts are labelled as data, not instructions.
- **Session timing.** Only the latest detail read changes selection and restores that branch's question/checkpoint drafts. An outstanding write blocks branch switching; acknowledgement clears only the submitted draft field. See [native draft/timing evidence](validation/Session-drafts-v1.md).
- **Session writes.** Creating, asking and saving checkpoints show waiting feedback. Submitting a question clears the preceding answer inspector; Retry retains its request/key and leaves any subsequently edited draft intact. Retry also waits for current Session read/write ownership and a successful detail observation; a successful branch switch clears the previous branch's retry. See [write-feedback evidence](validation/Session-write-feedback-v1.md) and [synthetic retry ownership evidence](validation/Memory-session-retry-ownership-v1.md).
- **Provider setup recovery.** Sessions offers setup instructions and explicit **Reload settings** for the fixed host configuration file. Refusal rules explain what needs changing. A read failure clears unobserved setup and offers **Read status again**. Reload is withheld during a held grant/request review or local send; the host separately refuses replacement during any Core send. The initial provider read uses stable native dependencies, avoiding a render/read loop. Even a failed reload reply triggers a fresh Core observation. See [setup guide](PROVIDER_SETUP_v1.md) and [synthetic recovery evidence](validation/Memory-provider-reload-v1.md).
- **Provider operation feedback.** External sends (including source extraction) offer **Stop locally**, retain terminal results, and distinguish a requested stop from completed local cancellation. This does not establish remote cancellation or whether a request reached the service. Failed extraction keeps Close and an explicit read of saved suggestions, which never resends or applies suggestions. See [synthetic operation evidence](validation/Memory-provider-operations-v1.md).
- **Provider session ownership.** Native Provider actions and running sends report their busy state to Sessions. During that work, branch switching, new sessions, local Mock sends and checkpoint writes wait; the inspector retains local cancellation. Parent session writes/detail reads also withhold Provider controls. Each branch owns a fresh Provider panel, and completion refreshes the original branch while preserving a later unsent draft. See [synthetic ownership evidence](validation/Memory-provider-session-v1.md).
- **Session observation recovery.** A failed detail read retains the previous observation, labels it as such and offers **Read session again** even for nonretryable errors. The explicit read targets the attempted branch; it never replays a send or write. New session writes/Provider actions wait for a successful detail read, while drafts remain editable and branch reads remain available. An ordinary **Refresh saved session** also reads the current branch. See [synthetic recovery evidence](validation/Memory-session-observation-v1.md).
- **Finding and reading Sessions.** A local [Session/branch ID filter](validation/Memory-session-id-filter-v1.md) operates only on the observed list, preserves the open branch and unsent drafts, and never issues an IPC lookup. [Visible row/header identities](validation/Memory-session-visible-identities-v1.md) distinguish branches; header selection changes only after a successful detail read. [Readable event metadata](validation/Memory-session-event-metadata-v1.md) retains each saved ISO timestamp, literal message and local Mock attribution. A [bounded-history note](validation/Memory-session-history-boundary-v1.md) explains the pinned Core's latest-200-event view without implying deletion or backend paging.
- **Workspace call re-observation.** Sessions reads the Core's `operation_list` on mount and serially while visible. Its workspace call section filters external sends, re-observes active IDs with the existing operation watcher and offers local cancellation. The inspector's watched call is excluded from that list while active. No request or draft is cached across page switches, and workspace calls are not attributed to the selected session. The live Core's operation table is the limit of this recovery; process/Vault resets still require reading saved session records. See [synthetic list/return evidence](validation/Memory-workspace-calls-v1.md).
- **Local ledger recovery with providers off.** A disabled/invalid native setup does not hide saved invocation records or the local interruption plan/confirmation flow. These use Core ledger commands without enabling a transport or showing external prepare/send/key controls. Held operation feedback also remains visible through setup-read failure. See [synthetic offline-ledger evidence](validation/Memory-provider-off-ledger-v1.md).
- **Cancellation timing.** The shared watcher consumes the Core cancellation acknowledgement immediately, keeps it separate from terminal completion, rejects another operation's reply and ignores earlier in-flight reads after that acknowledgement. A completed cancellation reply is observed once. Failed status reads retain the last observation with recovery. See [synthetic cancellation ordering evidence](validation/Memory-operation-cancel-ack-v1.md).
- **Native guidance.** Home describes the installed-producer connection and the reviewed external-request path. Lock/release/Exit text explains local model stopping and reading saved outcomes after reopening; hiding the window keeps calls running. See [guidance scope and evidence](validation/Memory-native-guidance-v1.md).
- **Suggestion queue recovery.** Ambiguous multi-step application requires reading saved job progress before a new batch; it never blindly retries the loop. Previous rows remain labelled until a successful read, and Close waits for admitted work. Reading suggestions never sends or approves them. See [synthetic queue recovery evidence](validation/Memory-extraction-recovery-v1.md).
- **Suggestion source ownership.** Next part waits while the mounted suggestion action/operation is active. Preview retains the original proposal and separately shows the current candidate's identity, revision, status and changed content; accepted candidates are not described as pending. See [synthetic range and candidate evidence](validation/Memory-source-suggestions-v1.md).
- **Suggestion model choice.** The owner can choose among observed configured destinations before preparing. The chosen model needs its own extraction grant and stays fixed through exact-body review, sending and reading that job. Selection itself sends and grants nothing. See [synthetic two-provider evidence](validation/Memory-extraction-provider-choice-v1.md).
- **Suggestion field compatibility.** Fixed-Core consumer tests cover a fake Anthropic response, one-step saved cursor progress, pending/current candidate metadata, edited ordinary approval and Core-owned Session job recovery IDs. Proposal/candidate text does not stand in for approved memory content. See [embedded-Core evidence and limits](validation/Memory-native-extraction-fields-v1.md).
- **Saved suggestion reads.** Sessions lists the saved header's suggestion runs and explicitly reads their existing response by Session/run IDs, including with providers off. Only the latest read publishes, and switching sessions/branches invalidates prior preview state. Reading itself does not apply or approve suggestions. See [original read-only Session recovery evidence](validation/Memory-saved-suggestions-v1.md).
- **Saved suggestion application.** After a successful read, the owner can explicitly add remaining local suggestions to the review queue, with no new model request. Session/job ownership stays fixed during the write; ambiguity requires reobservation before another batch, and a failed parent Session refresh blocks subsequent writes. See [synthetic and embedded-Core local application evidence](validation/Memory-saved-suggestion-apply-v1.md).
- **Suggestion batch lifetime.** Leaving a mounted source/Session flow stops later application submissions and result reads. An already admitted step may finish; return through saved Session suggestions to observe its cursor. This does not undo work or cancel a model remotely. See [synthetic unmount evidence](validation/Memory-suggestion-lifetime-v1.md).
- **Saved queue resume.** An observed paused job offers an explicit local resume followed by a saved read. It never sends or applies suggestions automatically; ambiguity requires reobservation and the same ownership/lifetime rules apply. See [synthetic and fixed-Core pause/resume evidence](validation/Memory-suggestion-resume-v1.md).
- **Source queue resume.** The original source suggestion view also withholds application while paused and offers explicit local resume, then rereads. It shares saved-job lifetime and ambiguity handling; applying still needs another gesture. See [synthetic source recovery evidence](validation/Memory-source-suggestion-resume-v1.md).
- **Saved responses.** Recognized completed local Mock records show their saved status, literal statements and source revisions in the transcript. A keyboard-accessible disclosure retains the exact recorded text; unknown/malformed formats and user messages stay literal. No answer or request is recomputed. See [transcript reading evidence](validation/Session-transcript-v1.md).
- **Saved answer Context.** Recognized local Mock responses offer an explicit saved-record lookup, then a separate Context navigation. Dispatch identity, verified hash, local destination, capsule/inspection identity and selected Session/branch must agree before navigation is offered. Failed reads can be repeated without another answer; branch changes discard the lookup, late replies cannot publish into the new branch, and parent Session ownership withholds the controls. The Context surface performs its own fresh read. See [synthetic journey and fixed-Core field evidence](validation/Memory-saved-mock-context-v1.md).
- **Saved Context focus.** A completed lookup restores focus to its explicit navigation or read-again control only when the reader has not moved focus elsewhere. Retry shares that path; parent ownership and unmount discard pending handoffs. See [controlled browser focus evidence](validation/Memory-saved-context-focus-v1.md); physical Windows keyboard and Narrator acceptance remain separate.
- **Explorer reads.** Each submitted query owns fresh rows and selection. Unobserved results remain unknown, and errors do not imply an empty search. Load more appends a Core page; a stale cursor keeps already observed rows with its error. Refresh results restarts at the first page with a new submission. See [paging and read-recovery evidence](validation/Explorer-feedback-v1.md).
- **Explorer keyboard.** Up/Down starts from the focused row and moves selection and focus together, bounded at the first/last loaded row. Space then activates that row. Search and toolbar arrows retain their own behavior. See [native keyboard evidence](validation/Explorer-keyboard-v1.md).
- **List reads.** Candidate counts and session lists stay unknown before observation, and failed reads cannot claim an empty list. Retry preserves unsent drafts. See [candidate/session read evidence](validation/List-read-feedback-v1.md); controlled read errors do not prove real storage recovery.
- **Import observation.** Recorded-import counts stay unknown until read. Explicit list refresh/recovery retains previous rows, file preview and account alias, while Start/Resume and their held retries wait for a successful current observation. An unobserved duplicate reference cannot be treated as a completed prior import; an observed interrupted import still requires Resume. Picker/preview retries remain available as reads. See [synthetic import recovery evidence](validation/Memory-import-observation-v1.md).
- **Import alias admission.** New Start and Resume requests validate their actual alias against the pinned Core's 1–64-character ASCII rule. Saved scopes and held original retries remain independent of later local drafts. See [DOM and boundary evidence](validation/Import-alias-admission-v1.md).
- **Memory lifecycle.** All Memory collections use the existing Vault gate during an observed host change or Exit, even while Core still reports open. Switching collections cannot reveal actions; reopening observes lists afresh. See [synthetic lifecycle evidence](validation/Memory-lifecycle-gate-v1.md).
- **Native Home.** Activity is described as using its separate producer. Observed Exit takes precedence over open Vault/queue information; unknown Memory status stays unknown and never implies no Vault. See [synthetic Home status evidence](validation/Home-status-observation-v1.md).
- **Settings startup observation.** Explicit startup reads retain and label failed prior observations, withhold changes until a successful read, and remain read-only during Exit. Local/observed Exit blocks the startup switch; header/Settings open indicators respect lifecycle state. `npm test` includes DOM-model assertions for Settings, Home and the Memory lifecycle; these are not native/browser acceptance. See [verification and limits](validation/Settings-exit-ownership-v1.md).
- **Stop observation.** A later observed cancellation acknowledgement or terminal outcome retires obsolete local stop errors/Retry, including late stop failures. Pending unacknowledged failures stay recoverable, and canonical operation failures remain visible. The actual watcher, identity and cancellation fixtures run in `npm test`; see [DOM verification and limits](validation/Operation-stop-observation-v1.md).
- **Candidate pages.** The inbox appends bounded Core pages beyond its first 50 rows, reports total versus shown count, and offers a fresh first-page read. A failed/stale read retains previous rows and drafts but withholds writes until successful observation. Held action retries also wait for current list/dialog ownership, retaining their original arguments/key and later drafts. See [paging evidence](validation/Memory-candidate-paging-v1.md) and [synthetic retry ownership evidence](validation/Memory-inbox-retry-ownership-v1.md).
- **Candidate evidence.** Review rows retain original citation locators and explicitly read the cited source revision in bounded parts. Availability stays unobserved until reading; errors, hide and revised candidates invalidate stale source results. This local reader offers no model action or approval. See [source and paging-focus evidence](validation/Memory-candidate-source-v1.md).
- **Evidence reader focus.** Explicit candidate-source reads/pages/Retry restore focus to literal text or the read recovery control only while the reader still owns focus. Hide restores Show; revision/unmount discard pending intent. See [DOM focus evidence and limits](validation/Candidate-source-focus-v1.md).
- **Conflict reader focus.** Explicit current-conflict reads and Retry focus the literal saved record or its read recovery control while focus is still owned. Hide returns to Read; existing candidate keys discard old revision reads. See [DOM conflict evidence](validation/Candidate-conflict-focus-v1.md).
- **Approved source focus.** The approved-memory source reader restores explicit read/page/Retry focus to text or Show source under the same ownership rule. Source/revision/availability changes invalidate intent without requiring remount; suggestion ownership remains unchanged. See [DOM source/suggestion regression evidence](validation/Memory-source-focus-v1.md).
- **Suggestion return focus.** Closing a source suggestion panel returns to its Suggest memories entry after the control remounts, unless focus has moved elsewhere. Declining or leaving a request still performs no extra preparation, send or queue write. See [DOM return-focus evidence](validation/Source-suggestion-focus-v1.md).
- **Empty candidate edits.** Clearing an edit withholds acceptance and its submission handler, matching the pinned Core's zero-character refusal. Reject stays available; nonempty edits and held retries preserve their ordinary review flow and drafts. See [DOM evidence](validation/Candidate-empty-edit-v1.md).
- **Suggestion review route.** An observed saved job with pending candidates can explicitly open Memory's candidate inbox. Navigation is read-only and waits for current job/Session observation; candidate IDs/revisions identify the matching row. Edited approval still needs its ordinary plan/confirmation, and returning to Sessions reads the updated candidate status afresh. See [synthetic mounted-App journey](validation/Memory-suggestion-review-journey-v1.md).
- **Candidate explanation.** The inbox can expand a saved nonempty proposal reason as literal data without sending or writing. It remains separate from source evidence, conflicts and approval. See [saved reason evidence](validation/Memory-candidate-reason-v1.md).
- **Candidate conflicts.** Inbox exposes recorded conflict IDs/revisions and explicitly reads current saved memories for comparison. Changed revisions, failed reads and late replies remain separate from the reported conflict; reading does not resolve or approve anything. See [browser and fixed-Core comparison evidence](validation/Memory-candidate-conflict-v1.md).
- **Saved Core recreation.** Source suggestions name the Core-issued Session/run IDs for later recovery. A consumer test recreates the embedded Core and reopens its synthetic Vault with providers off, then reads the saved job/candidate review and approved edits from a fresh Session list. See [recreation evidence and its process/durability limits](validation/Memory-core-reopen-v1.md).
- **Partial paused recreation.** The fixed-Core consumer also recreates at paused cursor 1, recovers partial observations, refuses application while paused and separately resumes/applies from saved IDs without another fake transport call. See [partial recovery evidence](validation/Memory-core-paused-reopen-v1.md).
- **Candidate observation identity.** A candidate source reply must match its cited source ID/revision, and a conflict memory reply must match its cited memory ID. Mismatches fail the read and offer reobservation rather than displaying another record; current conflict-memory revisions may legitimately differ. See [controlled identity checks](validation/Memory-candidate-observation-identity-v1.md).
- **Memory inspector observation.** Memory details match record/summary IDs, expose an explicit local reread and withhold unobserved write controls while keeping correction drafts. Approved-memory and candidate source readers share exact source identity checks. See [inspector recovery and compatibility evidence](validation/Memory-inspector-observation-v1.md).
- **Context reads.** Preview preparation, capsule reads and request reads have distinct waiting feedback. Selected-but-unread capsules are not labelled unselected, and dispatch metadata does not claim unread actual-request contents. A new preview clears the old selection, and a failed replacement preserves its query without implying an active read. See [Context read evidence](validation/Context-read-feedback-v1.md).
- **Context observation ownership.** Saved capsule/inspection and dispatch/capsule IDs are checked before publication. Verified requests must match the observed saved hash; actual hash mismatches remain explicit. Local rereads recover nonretryable errors without compiling or sending, and capsule rereads invalidate old requests while preserving drafts. See [controlled Context ownership and fixed-Core field evidence](validation/Memory-context-observation-v1.md).
- **Saved question.** Context shows the query from its inspected Core capsule separately from the editable preview draft. Editing that draft does not change the selected capsule's question or decisions. See [saved-query attribution evidence](validation/Capsule-query-v1.md).
- **Picker previews.** Import publishes a native choice with its successful preview as one selection. A failed new preview cannot offer an import against an earlier file's display. A new restore folder clears the preceding validation before reading it. Cancelling a native choice retains the last valid selection. See [picker/preview evidence](validation/Picker-preview-v1.md).
- **Contrast cues.** Forced-colors media uses system-color outlines for current-page/pressed selection and a separate keyboard focus outline. Ordinary theme styles are unchanged. See [WebView2 media-emulation evidence](validation/Forced-colors-v1.md); real Windows contrast-theme and Narrator acceptance remain pending.
- **Native accessibility.** A focus-visible keyboard entry bypasses the titlebar and primary navigation into the named current main content. Session row names identify their saved session/branch even when dates and event counts coincide. [Windows UI Automation and keyboard evidence](validation/Native-accessibility-v1.md) covers all seven main names, actual form labels, session distinctions and modal isolation. It does not establish Narrator speech or complete W05.
- **Keyboard task journey.** A continuous synthetic review → memory/source → session/local Mock/checkpoint → saved Context/request/preview journey is reachable using owned-page keyboard events. Session acknowledgements restore the appropriate composer after disabling controls, while respecting focus moved elsewhere. See [task and native focus evidence](validation/Keyboard-journey-v1.md); physical input and Narrator speech remain separate gates.
- **Operations.** Each operation ID starts a fresh watcher. Import, import resume and index rebuild offer cancellation at safe points; verify and backup explain that they finish before locking or exiting. A cancellation request and progress counts remain separate from terminal success/cancellation. A failed status read offers Retry. See [operation feedback evidence](validation/Operation-feedback-v1.md).
- **Review confirmation.** Waiting for the result is explicitly explained, and the pending modal blocks platform/keyboard dismissal while retaining close-event recovery. A read-only observation confirms Retry preserves its payload and key and replays the actual receipt. See [confirmation timing evidence](validation/Confirm-feedback-v1.md); simulated delivery errors are not storage-failure proof.
- **Quick Search** (`src/shell/QuickSearch.tsx`). Ctrl+Alt+M opens a hidden native window for literal search of approved memories, limited to eight current results. Escape, blur, close, returning to main and Vault lifecycle transitions clear query/results and invalidate delayed reads. It provides no detail, source excerpt, picker or mutation. The tray and Settings provide manual opening when a shortcut conflicts. `--hotkey-key <single ASCII letter>` explicitly selects another Ctrl+Alt combination for that launch; the default is M and no preference is persisted. The owned Windows message thread unregisters and joins on exit. Settings and Core companion status report registration, conflict or unavailability.

## Build and checks

Prerequisites:
- The pinned Rust 1.98.1 GNU toolchain.
- Node 24.15.0 or later.
- WebView2.
- A MinGW C compiler for Memory's bundled SQLite, for example MSYS2 UCRT64. Its `bin` must come before the Rust toolchain's `bin` in `PATH`.

The first build after a new pin needs one online fetch. Builds after that work offline from Cargo's Git cache.

```powershell
$env:Path = "C:\msys64\ucrt64\bin;$env:USERPROFILE\.cargo\bin;$env:Path"
cd apps/desktop/src-tauri
cargo fetch --locked                  # once per machine, cache or pin
$env:CARGO_NET_OFFLINE = 'true'
cargo fmt -- --check
cargo test --locked                   # adapter and companion unit tests, pinned-Core rendered-field tests
cargo clippy --locked --all-targets -- -D warnings
cd ..
npm ci
npm run check
npm test
```

## Bumping the pin

1. Read the new rows in Memory's compatibility log, `docs/integration/RUNTIME.md`. Review `git log <old>..<new> -- crates contracts apps/workspace` in the Memory repository.
2. Set `rev` for both Memory dependencies in `apps/desktop/src-tauri/Cargo.toml` to the new full SHA. If Memory changed an exact workspace pin (for example `serde_json`), align the desktop's own exact pin with it.
3. In `Cargo.lock`, replace the old revision with the new one on the Memory `source` lines only. Then run `cargo fetch --locked` online and `cargo metadata --offline --locked`. If Memory's manifests changed its dependencies, `--locked` fails. Only then run `cargo update -p enouia-memory-workspace -p enouia-memory-contract`, and revert any re-resolution of unrelated packages. That command can also move sibling edges (for example `syn`, `windows-sys`).
4. Update `docs/integration/memory-pin.json`: the revision, the Memory surface aggregate, `contract` (schema version and command count) and the date.
5. Adapt the adapter and the surfaces to what the log asks for. Keep `WRITES` equal to the contract.
6. Fetch the new revision into a Memory checkout. Then run every check above, the smoke test and `node scripts/check-memory-integration.mjs --memory-checkout <dir>`. The checker reads the surface manifest committed at the pinned revision, whatever the checkout's HEAD is. Record the result in a validation note.
7. Commit `Cargo.toml`, `Cargo.lock`, the pin record and the adapter changes together.

Never commit a path dependency, branch, `[patch]` or a lockfile produced by a local override. Builds use `--locked`, so a stray override fails.

## Boundaries

- **Activity & Usage.** It stays independent: its own data root, runner, scheduler and delivery. Nothing from Activity enters `memory_call`. Memory never reads Activity.
- **Cloud stages.** Runtime implements no Provider protocol, MCP endpoint, gateway, replica or sync. When Memory ships them they arrive through a pin bump, or through a Host client after MV-8. Memory's native text Provider path (MV-7, ADR-MEM-48) is hosted under [ADR-032](adr/032-memory-native-provider-setup.md): off without the owner's `memory-providers.json`, keys only through the native credential prompt.
- **Runtime-local Core crates.** `enouia-memory`, `enouia-session`, `enouia-context`, `enouia-provider` and `enouia-core-contract` are frozen history (ADR-025). Do not extend them, and do not mix their DTOs with Memory's.
