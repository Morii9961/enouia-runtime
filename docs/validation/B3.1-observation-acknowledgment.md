# B3.1 observation-gated pending acknowledgment

Date: 2026-09-28. Scope: one locked observation followed by one immutable-generation commit that records public evidence and clears the exact pending batch. It does not run collection, SSH transport, polling, scheduling, or a production cutover.

The orchestration first calls the origin-bound public observer. Only a fresh manifest, exact public Activity bytes, matching hash and three-source outcomes allow the commit. The store checks the pending sequence and exact byte hash again, validates that the observed Activity hash is the pending batch's canonical public data, preserves the local archive and high-water sequence, and writes origin, sequence, hashes, and times to `publicationObserved` in `delivery.json` in the same new generation that omits `pending.json`. Normal commits still reject pending clear. Recovery recognizes an older pending generation with the same sequence only when its exact hash and canonical public hash match this receipt; otherwise it reports a conflict. Prior generations remain available for audit. A failure before the pointer switch leaves the old pending generation selected; if the complete new directory was already published, recovery blocks automatic retry for reconciliation. The existing writer's post-switch rule requires rereading `CURRENT` after an ambiguous error.

Synthetic Windows tests verify successful observation and atomic pending-clear state, including the evidence record, unchanged archive/sequence, and a subsequent run-start decision for sequence 43. A stale manifest leaves the selected pending generation unchanged; an incorrect pending hash cannot authorize a clear. A separate acknowledgment fault matrix injects interruption after manifest flush, after publishing the complete new directory but before pointer switch, and after pointer switch. It verifies retry of the old pending, conservative conflict, and continuation at sequence 43 respectively. This is process-interruption evidence, not power-loss durability. The test evidence does not prove a real receiver accepted a sequence or activation against a public origin. Only the trusted observation orchestration should supply `PublicationEvidence` to the store API.
