# A1.2 index/retrieval design validation

Date: 2026-10-02. Baseline: `a30058e`. Scope: backend design, executable SQL candidate schema and an isolated synthetic in-memory development probe. No Runtime SQLite adapter, persisted database, frontend change, A1/A2 completion or production activation.

## Artifacts and design review

[ADR-021](../adr/021-index-and-retrieval.md), [index v1](../MEMORY_INDEX_v1.md), [retrieval v1](../MEMORY_RETRIEVAL_v1.md) and [the SQL design](../../contracts/vault/memory-index-v1.sql) define generation/policy binding, metadata/search projections, exact historical content ownership, bounded rebuild/publication, literal short/CJK queries and deterministic scope/ranking. Existing Memory/Session/Capsule/IPC schemas and Rust dependencies are unchanged. Current-scope notes reflect the user's separately progressing frontend work.

Compared the design to Vault ADR-020, `MemoryLedger::from_snapshot`, `validate_sessions`, `RankedMemory` and `compile_ranked`. Context receives canonical IDs with integer ordinals and one classification; compiler budget/inclusion semantics are preserved. Reviewed full-union sorting before cap, same-Session checkpoint admission, inactive/candidate exclusion, whole-field boundaries, full projection equality and index-versus-canonical commit separation.

Read SQLite's primary [FTS5](https://www.sqlite.org/fts5.html), [transaction](https://www.sqlite.org/lang_transaction.html) and [pragma](https://www.sqlite.org/pragma.html) documentation on this date. The tokenizer/short-query and database-check limits are captured in the contract; scope lanes/ranking are Enouia policy, not SQLite relevance behavior. No packaged library/version was selected.

## Executed development probe

Command from repository root: `python scripts/check-retrieval-design.py`.

Actual environment: local Python built-in `sqlite3`, SQLite **3.53.1**, with the specified FTS5 trigram table successfully created. The schema is executed in `:memory:` only. Input is [literal-v1.json](../../tests/fixtures/retrieval/literal-v1.json), explicitly a synthetic projection corpus, not a validated canonical Vault bundle.

Result: **48 checks passed** — 18 expected lexical query results in each of two opposite insertion/rebuild orders (36), refusal of not-ready/mismatched bindings and FTS projection changes in both builds (6), refusal of changed normalized projections (2), and four invalid query bounds/control cases (4). Cases cover CJK 1/2/3-character terms, ASCII folding, literal operator/quote/wildcard punctuation, separate-field intersection without concatenation, active/status/candidate-marker/time/validity/project predicates, inclusive equal validity endpoints, exact-tag-before-recency ranking, Memory ID ties and result cap.

Construction runs database integrity, foreign-key checks and FTS integrity checks. It compares every synthetic search field/FTS row to its independent fixture projection. Reverse construction returns exactly the same expected IDs/order. These checks establish the SQL/text-query subset on this development library; they do not establish production model/source validation or canonical-file hash binding. The fixture's candidate marker tests corpus exclusion only, not the real candidate lifecycle.
