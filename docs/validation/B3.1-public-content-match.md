# B3.1 public Activity content matching

Date: 2026-09-28. Scope: pure verification of already fetched public manifest and Activity JSON bytes against one frozen pending batch.

The matcher requires a fresh v1 manifest with exact UTC timestamps and a `validUntil` no later than 15 minutes after generation. It rejects a manifest generated more than five minutes in the future. The activity entry must use the exact `/status-data/activity/<hash>.json` path, and its SHA-256 must match both fetched public bytes and the batch's canonical ActivityData bytes. All three source `attemptedAt`, `succeededAt`, and `result` records must match the frozen batch. This prevents an all-failed batch from being considered observed solely because its unchanged data hash was already public.

The returned `MatchingPublicContent` records the manifest/data hashes and observation timestamps. It is content evidence only: no HTTP origin, redirect, response status, or fetch-limit claim is made here. The future read-only fetcher must enforce those boundaries before content matching can support a pending-clear commit. The manifest does not contain a sequence receipt.

Four deterministic tests cover exact content/outcomes, stale and future manifests, equal data with a different source attempt, changed public bytes, wrong path, and missing activity. The full workspace has 109 tests. `cargo fmt --all -- --check`, `cargo test --workspace`, `cargo clippy --workspace --all-targets -- -D warnings`, and `git diff --check` passed offline with installed Rust 1.98.1 GNU. No HTTP request or production state was used.
