# B2.1 Windows Activity single-writer lock

Date: 2026-09-27. Scope: the first platform primitive for the separate Activity store. `WindowsActivityLock` implements the shared `LockProvider` port for an absolute `sync.lock` path inside an existing Activity root. It canonicalizes the parent, rejects a pre-existing reparse-point lock file, and opens the lock with `share_mode(0)` and `FILE_FLAG_OPEN_REPARSE_POINT`; the opened handle is checked again. The returned guard owns the file handle until dropped. A leftover file after a crash is ordinary; ownership is the open handle, not file presence or a PID/time stamp.

The [Rust Windows `OpenOptionsExt` documentation](https://doc.rust-lang.org/std/os/windows/fs/trait.OpenOptionsExt.html) states that `share_mode(0)` prevents another open while the handle is live. [Microsoft's `CreateFileW` sharing rules](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-createfilew) identify a conflicting open as `ERROR_SHARING_VIOLATION` (32). The adapter maps that code to local `busy`; other I/O failures map to `storage_failed`. No path or raw OS error enters the structured public error.

Windows tests verify stale-file reuse, canonical alias contention, guard release, invalid/unavailable paths, and a separate OS process being excluded until its holder process exits. This lock does not yet prove data-root allowlisting, resistance to a concurrent path replacement, atomic generation visibility, or power-loss durability. Those are B2 generation-store gates before production use.

Checks: `cargo fmt --all -- --check`, `cargo test --workspace` (75 tests, including four lock tests), `cargo clippy --workspace --all-targets -- -D warnings`, and `git diff --check` passed offline with the installed Rust 1.98.1 GNU toolchain. No Activity archive, scheduled task, upload, Memory/Context state, or Moriium checkout was changed.
