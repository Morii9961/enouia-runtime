# B3.1 origin-bound observation orchestration

Date: 2026-09-28. Scope: one read-only observation of a locked pending batch through a bounded public-fetch port. A concrete HTTP adapter is still pending.

The observer validates a configured HTTPS origin (or HTTP loopback for isolated tests), fetches only `/status-data/current.json`, and accepts a referenced activity path only when it is exactly `/status-data/activity/<64-lowercase-hex-hash>.json`. Both responses must have status 200, their final URLs must equal the requested URLs, and no redirect may have occurred. The fetch port receives 15-second deadlines and 1 MiB/4 MiB body limits; the observer checks returned sizes again. It then applies the separate freshness, exact public-byte hash, and three-source outcome matcher. The writer lock remains held and pending is unchanged.

Four Windows tests use synthetic generations and a fake fetch port. They cover a matching observation, invalid origins, redirect refusal, cross-origin final URL, non-200 status, both size limits, timeout, stale content, and unchanged pending bytes. The full workspace has 113 tests. `cargo fmt --all -- --check`, `cargo test --workspace`, `cargo clippy --workspace --all-targets -- -D warnings`, and `git diff --check` passed offline with installed Rust 1.98.1 GNU.

The fetch port is an explicit contract: its eventual implementation must enforce body/deadline limits and report every redirect accurately. These tests do not establish a real HTTP connection, TLS validation, publication in production, or permission to clear pending.
