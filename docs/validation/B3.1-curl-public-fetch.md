# B3.1 bounded public HTTP fetch

Date: 2026-09-28. Scope: the Windows `PublicFetcher` adapter using a configured absolute `curl.exe` path and the existing job-owned `ProcessRunner`. It performs one GET per call and reports the response to the origin-bound observer; this feature does not clear pending or activate a scheduled run.

The adapter disables user curl configuration first, disables redirect following, restricts protocols to HTTP(S), rejects URL credentials, sends the body to stdout and a three-digit response code to stderr, and caps transfer time and body size. HTTP without TLS is reserved for the observer's loopback origin. A redirect response is reported as redirected and rejected by the observer. The Windows process runner adds an independent output cap and kills its job on timeout, cancellation, or capture overflow. The adapter does not parse curl's error text into public data.

The installed Windows curl 8.21.0 was tested against an isolated in-process loopback HTTP server: a 200 response preserved binary body bytes, a 302 response was identified without following its target, and an oversized response failed. The test exposed CRLF in Windows curl's write-out line; the parser accepts CRLF or LF. This is local transport evidence, not a live-publication or third-party CDN test. The curl command flags and write-out behavior were checked against the [official curl manual](https://curl.se/docs/manpage.html).

The observer also permits a loopback HTTP origin without an explicit port; the adapter now accepts that form. Curl receives a decimal-second deadline, and the job-owned process runner enforces the same supplied duration. A slow loopback response with a 100 ms deadline returned before 400 ms in the local test, confirming that the adapter no longer adds an extra second. This does not measure network latency or establish a production SLA.
