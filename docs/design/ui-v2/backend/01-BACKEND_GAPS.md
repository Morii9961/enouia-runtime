## 0. 结论

**已经能用的**：Core-7 的有界分页与详情、知识 / 采用 / 注意力 / 有效性四条状态轴、五种时间（发生、有效、学到、来源捕获、修订）、证据与生成依赖分开、原始收据、推导与回退邻居、带完整 trace 的召回模拟。来源记录（source-v1）已经保留原会话 ID、原消息 ID、原时区、时间精度、说话人角色和 locator，比初稿以为的完整。

**接真实数据之前必须补的**：下表标「阻塞」的 16 项，可以分成四类：

1. **记录格式**（G02、G09、G10、G14 的会话记录，以及降级项 G17、G19）：新根初始化之前要定，否则以后是整库迁移。由 [02](02-MEMORY_INIT_REQUIREMENTS.md) 给出字段，本报告的修复会话负责把字段写进契约。
2. **只读投影与读取端口**（G01、G03、G04、G05、G06、G07、G13、G18 的共同规则，以及降级项 G15、G16、G23）：不改记录，可以一项一项交付，前端每接一项就把对应视图从合成换成真实。
3. **写入路径**（G08 主人动作、G12 MCP 进不了自动化根）：前者经 Runtime 的原生入口，后者归 [03](03-MCP_REQUIREMENTS.md)。
4. **切换**（G11 真实 Vault 采用即 Core-8，G20 新旧两个库）：整件事的出口，不是一个独立功能。

## 2. 逐项说明

每项写：现在是什么（证据）、前端要什么、建议的修法、验收。所有新读取能力都沿用 Core-7 的规则：**先授权再计数**；隐藏的条目不能通过计数、空位、边或簇名泄露；游标绑定快照、筛选与敏感度上限；结果写明覆盖范围，不说成全库或整个人生。

### G01 · 列表规模

- 现在：`read-model-v2.schema.json` 的 page `items` `maxItems: 32`，`matched_in_scope` 与 `unknown_event_time_in_scope` 都是 `maximum: 128`；`CORE7_READ_MODEL.md` 写明范围最多 128。
- 前端要：记忆格一页 60–100 条，滚动续页；列表与星图要知道「共 Y 条」。合成星图按 200 / 700 / 1,000 / 5,000 测过，真实库按几千到几万条设计。
- 修法：去掉 128 的范围上限；单页上限提到 100（或按输出字节上限自然截断，已有 1 KiB–256 KiB 的调用方上限）；计数给精确值，或在超过某个阈值时给 `count_exact: false` 与下界，不能静默截在 128。游标规则不变。
- 验收：合成根 20,000 条，按任意筛选翻完全部页，条目不重不漏；删除或改策略后旧游标被拒；计数与逐页累加一致。

### G02 · 短标题

- 现在：记忆只有 `content`（1–16,384 字符），没有标题字段。
- 前端要：一行能读完的标题（建议 ≤ 60 字符，与内容同语言），用在记忆格、列表、时间线条目、星图标签、Inspector 标题和 Quick Search。前端截 `content` 只能当兜底，会截断在句子中间。
- 修法：记录字段，形成时与内容一起产出、一起版本化（字段定义见 02 §4）。参考：folio 的形成模型同时产出 `suggested_name`，Ombre-Brain 的 `hold` 接受调用方给的 `title`。
- 验收：合成形成流程产出的每条记录都有标题；修订内容时标题随修订；标题不出现内容里没有的信息（反例测试）。

### G03 · 时间分桶与聚合

- 现在：只有按事件窗口过滤与「未知事件时间」计数，没有按天 / 月的分组。
- 前端要：选一条时间轴（发生 / 学到 / 来源捕获），给时区、粒度（日 / 月）、窗口，返回每桶计数与未知桶；覆盖日历另要按层计数（收到的材料 / 暂存 / 已采用）。时间小地图要一年 365 个日桶。
- 修法：只读端口，暂名 `memory_time_buckets_native`。桶边界按请求的时区计算；区间型事件（G10 的 `bound = span`）按「跨越的每一天都算」还是「只算起点」要在返回里写明。零只表示「所选范围内没有记录」。
- 验收：与逐条分页统计结果一致；跨时区边界的合成例子（UTC 16:00 前后）落在正确的本地日。

### G04 · 全库图投影与带类型的边

- 现在：详情的 `neighbors` 只有 `derived_from` 与 `reversion` 两种（`MemoryLinkKind`），`maxItems: 32`；read model 的能力表里 `global_graph` 明确不可用。
- 前端要：星图一次拿到 200–5,000 个节点（ID、标题、种类、状态轴、主题、事件时间）与带类型的边；边分成**事实**（推导、回退、替代、纠正、同一段对话、同一实体）与**算法建议**（主题共现、语义近邻），后者带算法名、版本与「保留 X / 候选 Y」。
- 修法：只读端口，暂名 `memory_graph_native`，分块返回节点与边，带 `algorithm`、`version`、`snapshot` 与覆盖说明；布局由前端算（合成原型：5,000 节点的力导向布局在 Worker 里约 0.5 s，每帧绘制的 JS 时间约 1 ms）。详情的 `neighbors` 同时扩成带类型的边。
- 验收：隐藏条目的边不出现、也不影响计数；删除一条记录后重新读取，相关边全部消失；建议边的数量上限与候选总数同时返回。

### G05 · 主题成员规模

- 现在：主题是一条 `kind = theme` 的合成记录，成员走 `derived_from`，`maxItems: 8`。
- 前端要：一个主题挂几十到几百条记忆，用于泳道、聚类和筛选。
- 修法：主题记录本身保留（它的名字和摘要是一次合成）；**成员关系做成投影**：`memory → theme`、分数、算法、版本。参考 folio 的 `families.py`：纯派生、整体可重算，主人改名 / 钉住 / 解散在重算时按成员重叠（Jaccard ≥ 0.5）继承。主人对主题的改动是记录（G08），成员计算是投影。
- 验收：重算投影后主题 ID 不变（成员重叠足够时），主人改过的名字保留；删除成员后主题计数随之变化。

### G06 · 文字检索、筛选维度与计数

- 现在：原生分页的筛选只有种类、采用状态和事件窗口；没有文字检索（v1 有 FTS，新格式的读端口没有）。
- 前端要：文字（字面 + 别名）、种类、状态轴、主题、实体、项目、时间窗；每个筛选项旁边显示授权范围内的计数。
- 修法：给 `memory_page_native` 加 `text`、`theme`、`entity`、`project` 过滤和 facet 计数；检索索引随记录增量更新，属于可重建投影。
- 验收：中文与英文各一组合成数据；计数与实际结果一致；隐藏条目不进计数。

### G07 · 形成活动流

- 现在：只能看单条记录的历史与收据。
- 前端要：按时间倒序的事件流：收到材料、形成、采用、暂存、重评、合成、替代、纠正、淡出、归档、删除；每条带对象 ID、标题、时间、执行者（System 规则 / Owner）。
- 修法：只读端口，暂名 `memory_activity_feed_native`，从提交、收据和作业日志推出，分页；只含授权条目的元数据，不含正文。
- 验收：合成闭环跑一轮，流里的每个事件都能对应到一个收据或作业记录；锁定 / 删除后不再显示被删条目的标题。

### G08 · 主人动作

- 现在：新格式里形成与纠正都是 System 的工作（Core-3）；没有原生的主人入口。Runtime 的 Correct / Withdraw 现在是禁用按钮，前端不能模拟。
- 前端要：纠正（给出正确说法）、撤回（这条不该记）、保护 / 钉住（别淡出）、遗忘（删除，走影响预览）、改主题名 / 解散主题、合并或拆开实体。每个动作：计划 → 主人确认 → 提交，结果未知时可查询恢复。
- 修法：主人动作是**记录**（字段见 02 §5）：纠正 = 一条 `manual_assertion` / `user_statement` 来源 + 绑定目标的新修订，由 System 管线处理；撤回与遗忘走现有删除水位线；保护是主人的注意力策略标注，与机器注意力分开。原生入口由 Runtime 的 Workspace 调用，不经 MCP。
- 验收：前端只能通过真实计划 / 确认端口得到「Corrected by you」；Agent 和 System 不能产生主人动作记录（反例测试）。

### G09 · 实体与参与者

- 现在：每条记忆只有一个 `subject_id` 和可空的 `project_id`；旧数据模型的 SessionRecord 有 `participants`，新格式的记忆没有。
- 前端要：一条记忆涉及谁（主体、参与者、被提到的人）、什么项目、什么地方；实体有显示名和别名。
- 修法：记录字段 `entities[]`（实体 ID + 角色 + 支持它的证据）与实体记录（类型、显示名、别名、首次 / 最近出现）。实体合并是决定：有证据或主人确认才合并，模型只能提议（字段见 02 §4.3）。
- 验收：同名不同人的合成例子不被自动合并（04 文档场景 S05）；删除实体的唯一证据后，实体在读取中消失或标「无证据」。

### G10 · 事件时间的精度、区间含义与时区

- 现在：`formation-v2` 的 `event_time` / `valid_time` 只有 UTC `{from, until}`。来源层已经有 `time_precision`（毫秒…年、unknown）和 `original_timezone`，但记忆层没有。
- 前端要：分清「三月里的某一天」和「持续整个三月」；只知道月份时画成月范围，不画成 3 月 1 日 00:00 的点；按事件发生地的时区画日界线。
- 修法：记录字段 `precision`、`bound`（`within` / `span`）、`tz`、`basis`（原话说的 / 推断的 / 用了来源时间）。字段见 02 §4.2。这一项初始化之后补不回来。
- 验收：合成例子「前阵子」保持未知（04 文档场景 S08）；「三月」与「整个三月」形成不同记录；同一 UTC 时刻在 Asia/Shanghai 与 UTC 落在不同的日。

### G11 · 真实 Vault 采用

- 现在：Runtime 原生的自动记忆视图走 `memory_automation`（`memory-native-read-1`），只接受 `mode: synthetic_only`；真实 Vault 仍是旧的 owner-review 路径。
- 修法：Core-8，由 Runtime 的独立采用切片做（升 pin、适配器、整机生命周期），需要 Morii 另外授权。这里只列为出口。

### G12 · MCP 进不了自动化根

- 现在：进行中的 `MCP_NATIVE_AGENT_V1.md` 的格式矩阵写明：六个 MCP 工具只服务 schema-1 / `host-current-v2`；遇到 schema-2 / `automation-host-v2` 在解码之前拒绝；「V2 Agent reader/writer」延后。`memory_propose` 产生待定提议，`session_checkpoint` 产生临时检查点，都不进入自动形成。
- 后果：重新初始化之后，日常通过 Claude / Codex 等 Agent 发生的对话不会形成新记忆，UI v2 的 Formation、时间线、星图会停在初始化那一刻。
- 修法：归 [03](03-MCP_REQUIREMENTS.md)。

### G13 · 变化通知

- 现在：读端口都是一次性的快照读取；没有「从某个提交以来有什么变了」。
- 前端要：Formation 的事件实时到达、记录带的写入记号、列表与星图的增量刷新；不靠前端定时器猜。
- 修法：最小做法是在状态里给当前头提交 ID 和序号，再加 `memory_changes_since(commit_id)` 返回变更的 ID 列表（授权后）；以后可以改成推送。不在前端轮询全量页面。
- 验收：形成一条后，前端在下一次查询里拿到它的 ID；没有变化时返回空且很快。

### G14 · 会话与轮次

- 现在：`storage-v2` 只有 descriptor、current、source、memory、receipt、data、commit、publication；没有会话或轮次。来源记录带 `original_conversation_id` 与 `original_message_id`，但 Runtime 的 Sessions 表面读的是旧 Workspace 的 `session_list` / `session_detail`。
- 前端要：Sessions 列出对话、每段对话的轮次；记忆的 Inspector 能跳到那一轮并高亮引文；星图的「同一段对话」边。
- 修法：新格式里加会话 / 对话记录（对话 ID、平台、标题、参与者、起止时间、轮次数、分支）与按对话列出来源的读端口；证据 locator 能解析到轮次与字符范围（02 §3）。
- 验收：一段合成对话形成三条记忆，三条都能跳回各自的轮次；对话被删除后跳转显示「来源已删除」而不是空白。

### G15 · 冲突组与修订差异

- 现在：详情返回历史，但不返回 `disputed` 的对手方，也没有修订之间的差异。
- 修法：详情里加冲突组成员（双方当前修订与各自来源）和相邻修订的差异摘要（只给授权范围内）。

### G16 · 有效敏感度

- 现在：敏感度在策略里，读取条目不直接给。
- 修法：读取结果每条带有效敏感度（不改记录），前端用来提示与遮挡。

### G17 · 内容语言

- 修法：记录字段 `content_lang`（BCP 47，如 `zh-Hans`、`en`），形成时写入；事后推断不可靠。前端按它切换中文排版。

### G18 · 投影的共同规则

所有新投影（G03–G07、G13、G23）共用一套规则，建议在 Memory 写成一条 ADR：

- 带 `algorithm`、`version`、`snapshot`（来源提交 ID）与覆盖说明；
- 服从删除与撤回水位线：被删正文进入过的主题摘要、图边、计数、检索索引一起失效，重建不复活（04 文档场景 S12、S32）；
- 可整体删除重算；重算不改变任何记录、不改变对外显示的 ID；
- 读取时先授权再计数。

### G19 · 为什么形成

- 现在：形成决定里有 `interpretation`（`clear_self_report` / `inference` / `ambiguous` / `conflicting`）与规则版本，但读取条目只给知识、采用、规则版本，不给解释。
- 修法：读取条目带 `interpretation` 和一句形成说明（形成时由同一模型产出，见 02 §6，存为附注，不当事实）。

### G20 · 新旧两个库

- 现在：Runtime 原生表面读旧 Workspace（58 个命令）；新格式有独立的读端口；Core-7 能力表里 `legacy_owner_history` 不可用。
- 前端要：状态牌清楚说「当前读的是哪个库」；切换后，旧库里主人审核过的记忆在新界面里仍能看到来历（以前由你确认过）。
- 修法：初始化把旧库作为来源导入（02 §2），旧的主人审核记为主人确认类来源，不改写旧记录；状态里给「当前根」的标识与格式版本。

### G21 · 一条记录一个陈述

- 前端的格子、星点、时间点都假设一条记录是一个可显示单位。多事件的长段落在形成时拆开（folio 的 `grow` 拆成 2–6 条），不靠前端拆。归 S2 的形成规则。

### G22 · Context

- 现在：Context 表面用旧的 `context_preview`（会保存产物）；新格式只有 `simulate_native_recall` 与 `simulate_synthetic_recall`。
- 修法：新格式下给 Agent 的上下文（MCP 的 `context_get` 或其后继）与 Context 表面看到的必须是同一份 trace。归 S3 的读路径，S1 提供端口。

### G23 · 全库统计

- 修法：在 G01 / G06 的计数之上加一个统计端口：各状态、种类、主题、注意力的计数，带覆盖说明。首页和星图侧栏用。

### G24 · 以后

回看 / 淡出建议卡（Core-6 写明没有通知）与保存实验（Core-7 写明不可用）保持现状，前端继续标「不可用」。

## 3. 建议的修复顺序

## 4. 前端这边的承诺

- 每接到一项能力，把对应视图从合成换成真实，按 [SCREENS.md](../SCREENS.md)「三种状态」逐项采用；能力没到的视图继续标「Synthetic preview · not running」。
- 前端不模拟主人确认，不把「系统已采用」写成「你已确认」，不在前端算真值。
- 布局、颜色、动效都只在前端；后端不需要为星图提供坐标。
- 原生接入（升 pin、适配器）仍是 Runtime 的独立采用切片，需要 Morii 另外开始。
