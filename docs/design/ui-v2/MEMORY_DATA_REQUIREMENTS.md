# UI v2 对 Memory 数据格式与后端能力的需求

日期：2026-10-25。写给 Morii 与 Memory 仓库的实现者（Codex）。这是 Runtime 前端的需求说明，不是 Memory 的契约或 ADR；Memory 侧的决定仍按它自己的阶段与 ADR 做。

核对的版本：

- Enouia Memory `main` = `c9bf1be`（PR #55「integrate automated Memory core」，Core-1…Core-7）；读了 `docs/contracts/CORE1…CORE7`、`docs/design/DATA_MODEL.md`、`contracts/next/read-model-v2.schema.json`、`contracts/next/formation-v2.schema.json`。
- Runtime `redesign/v2`：pin `bf6bfd1`（workspace IPC v1，58 个命令）；原生自动记忆视图走独立的 `memory_automation`（capability `memory-native-read-1`），目前只接受 `mode: synthetic_only`。
- 前端需求来源：[SCREENS.md](SCREENS.md) 的五个工作区与十种状态、合成预览（Formation / Memory grid / Timeline / Constellation / Star map / Recall lab）、Memory UI 规格 §4–§9。

## 0. 结论

**能直接用的**（Core-7 已有，前端可以照着接）：有界分页列表与详情、知识/采用/注意力/有效性四条状态轴、五种时间（发生、有效、学到、来源捕获、修订）、支持证据与生成依赖分开、原始收据、推导/回退邻居、带完整 trace 的原生召回模拟。三种状态分开（旧 pin 真实 / 合成 / 以后采用）的原则两边一致。

**会卡住 UI v2 的缺口**（详见 §3）：

1. 规模：`matched_in_scope` 与几处数组上限是 128，单页 32；真实记忆库会远超这个量。
2. 没有短标题，只有一条最长 16 KB 的 `content`。
3. 没有全局时间线与按天/月的聚合（月→日时间线、覆盖日历都要）。
4. 没有图投影：邻居只有推导/回退，最多 32 条；Core-7 明确写着「global timeline/graph」不可用。记忆星图需要它。
5. 主题成员关系上不了规模：主题是一条合成记录，`derived_from` 最多 8 个父记录。
6. 原生列表没有文字检索，也没有按主题/人物/项目的筛选。
7. 没有「系统做了什么」的时间流（Formation 视图要）。
8. 没有可选的主人控制：纠正、撤回、保护、遗忘都没有原生入口（Core-3：形成与纠正是 System 工作）。
9. 没有人物/实体：每条只有一个 `subject_id` 和可空的 `project_id`。
10. 事件时间分不清「那个月里的某天」和「持续了一个月」，也没记录用哪个时区解释日期。
11. 真实 Vault 仍是旧的 owner-review 路径；自动化读取只开在合成根上（Core-8 才是真实采用）。

**重新初始化之前最该定下的**：§2 里标「写进记录」的几项。它们一旦写进真实数据，Core-5 写明「No old root is upgraded」，以后要改就是整库迁移。其余（主题归属、自动连线、标签、注意力、布局、聚合）建议做成**可重建的投影**，以后随算法升级重算，不必现在定死。

## 1. 原则：写进记录 vs 做成投影

回答「要不要自动打标签、自动与其他记忆建立联系」：

| | 写进记录（不可变、版本化、要迁移才能改） | 做成投影（带算法名+版本+快照，可删可重算） |
| --- | --- | --- |
| 判断标准 | 有来源证据支持的陈述，或 Morii 自己的动作 | 由已有记录和来源**推算**出来的东西 |
| 例子 | 内容、种类、发生/有效时间、条件、主体与参与者、来源引用、推导与回退、纠正、主人的保护与撤回 | 主题归属、共现连线、语义近邻、标签建议、注意力状态（Core-6 已是这样）、按天计数、星图布局 |
| 前端怎么显示 | 事实陈述，带「主体说过」等限定 | 永远标「算法建议 · 名称/版本」，不当事实，不当关系 |

理由：

- 自动标签与自动连线都会随模型和算法变好而变。烤进记录，以后每改一次算法都要改历史记录，还会把模型的猜测伪装成记录的一部分。放在投影里，换算法就是重算一次，旧记录不动。
- 研究笔记（Memory 仓库 `01-source-review.md`）已经指出：OmbreBrain-folio 的星图连线是共享标签的共现，最多保留 600 条，不是事实关系。我们的合成星图也是这样标的。
- 例外：**由证据成立的关系**（A 纠正/替代 B、A 由 B 推导、某段经历的参与者是谁）是陈述，要进记录并带来源。

## 2. 重新初始化前要定下的字段

「状态」列：✓ 已有、△ 部分、✗ 没有。「建议」列：**记录** 表示新根的记录格式里要有；**投影** 表示可以以后加。

| 字段 | 前端用在哪 | 状态 | 建议 |
| --- | --- | --- | --- |
| 短标题 `title`（≤ 60 字符，与 content 同一来源与解释） | 记忆格、列表、时间线条目、星图标签、Inspector 标题、Quick Search 结果 | ✗（只有 `content`） | **记录**：形成时一起产出，不可另行改写；为空时前端截 content |
| 事件时间的精度与语义：`precision`（instant / day / month / year）、`bound`（`within` = 发生在区间中的某处；`span` = 持续整个区间）、`tz`（解释日期用的 IANA 时区，如 `Asia/Shanghai`） | 时间线点/段/月范围的画法、「只知道是三月」、日界线一致 | △：只有 UTC `{from, until}`；来源记录有 `time_precision`，记忆层没有 | **记录**：不加就无法区分「三月某天」和「整个三月」，以后补不回来 |
| 参与者与实体 `entities[]`：`entity_id`、`role`（subject / participant / mentioned）、指向 EntityRecord（`type` person / project / place / organization / thing，`display_name`，`aliases`） | 人物/项目筛选、星图的人物节点、关系经历、Inspector 的「涉及」 | △：单个 `subject_id`、可空 `project_id`；DATA_MODEL 里 episode 有 participants，HostV2 维度里没有 | **记录**（实体本身和「谁参与了」）；实体合并/别名建议做**投影**，合并要有证据或 Morii 确认 |
| 内容语言 `content_lang`（zh-Hans / en / …） | 排版（中文取消字宽轴与字距）、搜索分词 | ✗ | **记录**（便宜，事后推断不可靠） |
| 证据引用的原文位置：来源 revision + locator + 引文范围 | Inspector 的「由什么支持」、高亮原句、跳到会话 | △：有 evidence 与 SourceRecord.locator；需确认 HostV2 的 CapturedSource 保留 `original_conversation_id`、轮次与 locator | **记录**：确认保留；没有就补 |
| 「同一段对话」 | 星图的「same conversation」连线、Sessions 跳转 | △：可由来源的会话 ID 推出 | **投影**（只要来源里有会话 ID） |
| 纠正与撤回 | Inspector 的 Correct / Withdraw（现在是禁用按钮）、「Corrected by you」 | ✗（原生没有主人入口） | **记录**：主人纠正 = 一条新的 `user_statement` 来源 + 绑定目标的新修订；撤回 = 删除请求走现有删除水位线 |
| 主人的保护/置顶 | 记忆格「钉住」、星图强调、不淡出 | △：AttentionProfile 有 protected IDs，但没有主人操作入口 | **记录**为主人的策略/标注（与机器记忆分开），注意力仍是**投影** |
| 主题归属 `memory → theme`（分数、算法、版本） | 主题泳道、星图聚类、主题筛选 | △：主题是合成记录，父记录 ≤ 8 | **投影**：主题记录本身保留；大规模归属做成投影 |
| 共现/语义连线（共享主题、相近时间、相似内容） | 星图虚线、「相关记忆」 | ✗ | **投影**：标算法；不越过授权，不自动变成事实关系 |
| 自动标签 | 筛选条 | ✗ | **投影**；如果要 Morii 自己的标签，另做一种主人标注**记录** |
| 情绪、重要度、置信度当成事实字段 | — | DATA_MODEL 旧格式有 `confidence`、`priority` | **不要**作为机器记录的事实字段。主观理解已是独立种类（`subjective_understanding`，staged）；重要度用注意力投影 |
| 敏感度在条目上可见 | 外发前提示、截图遮挡 | △：在 policy 里，条目里不直接给 | 读取结果里带上**有效敏感度**（不必改记录） |

另外两点要在初始化时写清：

- **ID 稳定性**：记忆、来源、实体、主题的 ID 一旦对外显示（URL、复制 ID、星图节点），就不能因重算投影而变。投影只引用这些 ID。
- **一条记录一个陈述**：前端的格子、星点、时间点都假设一条记录是一个可显示的单位。多事件的长段落应在形成时拆开，不靠前端拆。

## 3. 每个视图需要的读取能力

| 视图 | 前端需要 | Core-7 现在 | 缺口 | 建议的能力（只读、先授权后计数） |
| --- | --- | --- | --- | --- |
| 记忆格 / 列表（ref-01） | 上千条分页、按种类/状态/主题/人物/项目筛选、文字检索、各筛选项计数 | 分页 ≤ 32，范围 ≤ 128；筛选只有种类、采用、事件窗口 | 规模、检索、筛选维度、计数 | `memory_page_native` 去掉 128 范围上限（保持游标与快照绑定）；加 `text`（字面）与 `theme / entity / project` 过滤；加授权范围内的 facet 计数 |
| 详情 / 来源抽屉 | 当前修订、历史、来源原文、证据与依赖分开、跳会话 | ✓ | 会话跳转所需的会话 ID 与轮次要确认在来源里 | 保持；补来源的会话/轮次字段 |
| 时间：月→日（ref-02） | 按月、按天的条目与计数；选择轴（发生 / 学到 / 来源捕获）；未知时间单列 | 只有事件窗口过滤与未知计数 | 没有聚合、没有按天分组 | `memory_time_buckets_native`：轴、时区、粒度（月/日）、窗口 → 每桶计数 + 未知桶；条目继续用分页 |
| 时间：覆盖日历（ref-06） | 每天三层：收到的材料 / 暂存 / 已采用 | ✗ | 没有来源层的按天计数 | 同上，加 `layer`；零只代表「所选范围无记录」 |
| 时间：主题泳道（ref-08/09） | 主题列表 + 成员 + 各自事件区间 | 主题记录可读，成员 ≤ 8 | 成员规模 | 主题归属投影（§2） |
| 关联：邻域（现有 Constellation） | 选中对象的有界邻居 | ✓ 推导/回退，≤ 32 | 只有推导/回退两种 | 在同一接口加「同一段对话」「共享实体」「主题共现」等**带类型、带算法**的边 |
| 关联：记忆星图（全库） | 节点（ID、种类、状态轴、主题、事件时间）+ 带类型的边 + 覆盖说明；200–5,000 节点 | ✗（Core-7 明确不可用） | 整个能力 | `memory_graph_native`：授权后的节点与边，分页或分块，带 `algorithm/version/snapshot`，返回「显示 X / 共 Y」；布局由前端算（合成原型实测，生产构建、无头 Edge：5,000 节点 force 布局约 0.5 s，在 Worker 里；绘制每帧的 JS 时间 < 1 ms） |
| 形成：系统做了什么 | 按时间倒序的事件流：收到、形成、采用、暂存、重评、合成、淡出、归档、纠正 | 只有单条的历史与收据 | 跨条目的时间流 | `memory_activity_feed_native`：分页的操作记录（只含授权条目的元数据，不含正文） |
| 形成：冲突对照 / 修订 diff | 两条并排、差异、各自来源 | △：详情有历史 | 冲突组成员 | 在详情里返回冲突组（`disputed` 的对手方）与修订间差异 |
| 召回实验室 | 合成演示 + 原生解释 + trace | ✓（`simulate_native_recall`、`simulate_synthetic_recall`） | 保存实验不可用（规格接受） | 保持 |
| 回看 / 淡出建议卡 | 为什么此刻值得回看、为何暂不再提 | ✗（Core-6：无通知） | 整个能力 | 以后：只读的建议列表 + 解释；触发与冷却由 Memory 定义 |
| 可选主人控制 | 纠正、撤回、保护、查看历史 | 只有历史 | 纠正/撤回/保护 | 见 §2；每个动作走计划 → 确认 → 提交，结果未知时可查询恢复 |
| 真实 Vault | 上面全部接真实数据 | 合成根 only | Core-8 采用 | 新根初始化 + pin + 适配器；前端在能力未到之前继续标「合成」 |

所有新能力都沿用 Core-7 已有的规则：先授权再计数；隐藏的条目不通过计数、空位或边泄漏；游标绑定快照、筛选和敏感度上限；结果写明覆盖范围，不说成全库或全部人生。

## 4. 前端状态词与后端轴的对应

合成预览里的单个状态词，真实数据里来自几条轴的组合。实现时按这张表映射，不另造状态：

| 预览里的词 | 后端来源 |
| --- | --- |
| Adopted by system | `adoption = adopted`（`knowledge = attributed_statement`：显示为「主体说过」） |
| Held hypothesis / Uncertain / Disputed | `adoption = staged` + `knowledge = hypothesis / uncertain / disputed` |
| Consolidated | 种类 `theme` 的合成记录，或带 `change = synthesis` 的修订 |
| Fading / Archived / Protected | `attention`（投影，不是真假，不是删除） |
| Superseded | 有更新修订，或被另一条替代（需要 §3 的替代边） |
| Corrected by you | 需要 §2 的主人纠正；在那之前不能出现在真实界面上 |
| Not yet valid / Expired | `validity` |

## 5. 建议的顺序

1. **初始化之前**：Morii 与 Codex 确定 §2 中标「记录」的字段（标题、时间精度/语义/时区、实体与参与者、内容语言、证据位置、纠正与撤回、主人保护），在 Memory 仓库记 ADR，按 Core-5 的做法开新的根布局版本，不原地升级。
2. **初始化之后，前端接入前**：§3 里的「列表规模 + 检索 + 筛选」、「时间分桶」、「图投影」、「活动时间流」。它们都是只读投影，可以一项一项交付，前端每接一项就把对应视图从合成换成真实（按 SCREENS.md「三种状态」第 3 条，由集成负责人逐项采用）。
3. **以后**：建议卡、语义近邻（要向量时另做决定）、保存实验。

在这些能力到来之前，前端继续在浏览器演示里用合成数据设计，并保持「Synthetic preview · not running」的标注。
