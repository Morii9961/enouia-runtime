# 自检循环

设计质量最大的来源是**亲眼看着改**。这一份规定怎么截图、怎么看、怎么批评、怎么记录。

## 1. 截图

用 `tools/shot.mjs`（Playwright，Windows 上没有 Chromium 会自动尝试系统的 Edge / Chrome）：

```bash
node tools/shot.mjs --out .design/shots \
  nautical=http://localhost:4321/__design/03-nautical \
  riso=http://localhost:4321/__design/04-riso
# 常用参数
#   --widths 1440,820,390      三档宽度（默认）
#   --full                     整页长图（默认只截首屏）
#   --clip 0,0,720,480         截局部，用来 1:1 看细节
#   --dark / --reduced-motion  模拟深色 / 减少动画
#   --wait 800                 页面稳定后再等多少毫秒（动画多时加大）
#   --index                    额外生成 .design/shots/index.html 并排对比
```

脚本除了 PNG，还会为每张图写一份 `*.json` 指标：实际用到的字体、字号档数、颜色数、小于 11px 的文字数量、横向溢出、控制台报错。**先看指标，再看图。**

## 2. 怎么看

1. **用 Read 读取 PNG**，真的看。无法读图时在报告里写「无法读图，以下只基于指标」，并且不能写任何关于「好看」的结论。
2. 先看整页缩小的样子（眯眼），再看 1:1 的局部（`--clip`）。
3. 同时摆出另一个方向的截图，问：它们还够远吗？

## 3. 必答的问题

每一轮用文字回答，写进 `critique-log.md`：

1. **概念可见吗？** 不看文字，只看形状、色彩和排版，能看出「这是一台暗房 / 一张海图」吗？看不出就是装饰没对准概念。
2. **眯眼顺序。** 最先看到什么？第二？第三？是你想要的顺序吗？
3. **最不协调的三处**，写成可执行的修改：元素 + 属性 + 数值。例如「总览标题行高 1.1 → 0.95，字号 56 → 88」，而不是「标题再大气一点」。
4. **模板不会做的决定**还在吗？有没有在修改中被磨平成默认？
5. **距离。** 和最像的另一个方向比，哪两个轴仍然不同？
6. **中文。** 指标 JSON 里中文实际命中的是不是指定字体？行高、标点、中英文间距有没有问题？
7. **数据。** 最密的页面里，数字是否一眼可读？单位和时间范围是否就在数字旁边？

## 4. 可量的底线

| 项目 | 底线 |
| --- | --- |
| 字号档 | 至少 4 档；展示级与正文之比 ≥ 3（有招牌时刻的页面 ≥ 6） |
| 非中性色相 | ≤ 3 个 |
| 小于 11px 的文字 | 0（装饰性刻度除外，需注明） |
| 横向溢出 | 0 |
| 控制台报错 | 0 |
| 正文对比度 | ≥ 4.5:1 |
| 对齐线 | 主要元素的左边缘收敛到 ≤ 4 条竖线（数一数） |

底线不是目标，过了底线也可能很丑。

## 5. 修改规则

- 一次只改一件事：先结构，再字号反差，再颜色，再细节。
- 每一轮后重新截图，**对比改前改后**，不要只相信自己的修改。
- 至少两轮；第二轮要有实质变化，不能只是微调 1px。
- 不要为了通过底线把设计磨平。底线冲突时用风格化的方式满足它（比如小字体换成大写字距，而不是放弃小字体）。

## 6. critique-log.md 格式

```
## 第 1 轮 · <日期时间>
- 截图：<路径>
- 概念可见：…
- 眯眼顺序：1) … 2) … 3) …
- 三处问题与修改：1) … 2) … 3) …
- 模板不会做的决定还在：…
- 与最近方向的距离：…
- 中文：…
- 指标异常：…

## 第 2 轮 …
```
