# Future Claude Design usage in the existing Claude calendar

Decision recorded 2026-09-26. The requested public result is **one existing Claude calendar**: its daily token value should eventually include locally measured Claude Code and Cowork usage plus token usage reported for Anthropic's `claude_design` product. There is no fourth ActivityData source or separate Design calendar. This is a future extension; no collection, account access, archive migration, or public publishing is enabled by this document.

The current [architecture v0.3](../Enouia_Runtime_Architecture_v0.3.md) and ActivityData/batch v1 still describe `sources.claude` as Claude Code plus local Cowork, with `Asia/Shanghai` day labels. [ADR-019](adr/019-claude-design-usage.md) records the requested change in meaning and the gates before activation. Existing M0 contract fixtures, serialized bytes, and Moriium compatibility claims remain scoped to the three-source baseline.

## Source and measure

- Count only `total_tokens` attributed to the **`claude_design` product** for the selected Enterprise seat user by the [Claude Enterprise per-user token usage endpoint](https://platform.claude.com/docs/en/api/http/beta/organization/analytics/usage/list_by_user). This is a product-attribution measure, not a count of every action that produced a design. Do not derive tokens from a shared-limit percentage, activity count, project count, browser cache, or a Design template label.
- The [Analytics API guide](https://platform.claude.com/docs/en/manage-claude/analytics-api) says the cost/usage reports cover usage-based Enterprise plans; seat-based plans report only usage credits. An eligible organization, primary-owner-enabled Analytics API, `read:analytics` key, and the correct tagged user ID must be verified before this source is considered complete. A personal or ineligible account must remain unavailable. No key or user ID enters public data or repository fixtures.
- The [Claude Design guide](https://support.claude.com/en/articles/14604416-get-started-with-claude-design) says Design shares Claude's usage limits. Shared-limit progress is a different metric. The [Artifacts admin guide](https://support.claude.com/en/articles/16994751-artifacts-admin-guide-for-team-and-enterprise-plans) says its Design active-user analytics cover the standalone site, not designs made in conversations or Artifacts; those counts cannot fill this token series.

## Daily aggregation and local state

1. Use `products[]=claude_design`, `group_by[]=product`, `user_ids[]=<configured tagged user ID>`, and **`bucket_width=1h`** with explicit RFC 3339 bounds. Fetch enough UTC hours to cover each requested `Asia/Shanghai` calendar day. Validate every returned actor, product, bucket interval, and nonnegative safe integer; paginate to `has_more=false` with the same filters and range. Reject duplicate or overlapping buckets, incomplete pagination, and data after `data_refreshed_at`. The exact response parser and range algorithm need synthetic API fixtures before implementation.
2. Convert each complete UTC hourly interval to its `Asia/Shanghai` day, then sum with checked safe-integer arithmetic. Do not relabel a UTC daily bucket as a Shanghai day: a UTC day straddles two Shanghai dates. A completed query with no rows can establish zero only for a fully covered, sufficiently refreshed interval; missing pages, permissions, or delayed data are **unknown**, not zero.
3. Keep versioned **private component histories** for Code/Cowork and Design separately, including coverage and successful refresh times. Recompute the public Claude value from those components. Never add a new Design value onto an already combined `sources.claude` value. Preserve old Code/Cowork dates when a tool reports a moving window; replace explicitly revised component values, including downward corrections. Import existing `sources.claude` history as a reviewed Code/Cowork baseline, not as an already combined history.
4. The combined Claude source is successful only when every required component is complete for the attempted range. If Design acquisition is unavailable or incomplete after activation, retain the previous combined snapshot and its successful time, report a local failed/degraded attempt, and avoid publishing a Code/Cowork-only replacement. The API may revise recent dates; re-fetch its revision window and allow both upward and downward changes. Do not rewrite an immutable pending batch.
5. The v1 wire object can retain `sources.claude`, `metric: tokens`, and `timezone: Asia/Shanghai` **only after** the changed meaning is accepted by both producer and Moriium consumer. Public v1 has no component provenance, so the About label/explanation must describe the combined measure and its start/coverage date. The local UI may show component breakdown and unavailable/partial-coverage states without exposing account IDs. Until that coordinated change, the public Claude value keeps its original Code/Cowork meaning.

## Activation gates

- Confirm the account plan, seat attribution, endpoint access, and response shape with a bounded, authorized test; do not read or copy credentials while planning. Check controlled use through standalone Design, conversation/Artifacts Design, and Claude Code `/design` to detect attribution gaps or overlap with local Code logs. Stop on unexplained double counting.
- Create synthetic paginated hourly fixtures for Shanghai midnight crossing, explicit zero, partial freshness, missing page, duplicate/overlapping bucket, wrong user/product, safe-integer overflow, revised values, and component failure retention. Compare the resulting public bytes and status meaning with a coordinated Moriium change.
- Reconcile the old Claude archive and any pending v1 batch before changing the source meaning. Agree the About copy and coverage marker with the Moriium owner; verify receiver, publisher, static JSON, and About behavior in isolation. A wire-format change would require a new protocol version and both sides' acceptance; this document does not authorize one.

The Enterprise API is currently beta and this repository has no real response, plan verification, or component collector. These gates are therefore **unverified**.
